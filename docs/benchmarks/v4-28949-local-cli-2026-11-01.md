## Hidden oracle and the blocking finding

The sealed fixture invokes the actual v2 adapter, actual OpenCode2Client, and actual ProviderSessionManager, with injected in-process HTTP/MCP transport, `external:false`, event sink/projections and in-memory SQLite. No real OpenCode process, network listener, production data, real MCP token or global settings were used. Identity tools authenticate distinct synthetic scope; last-match permission rules and location-scoped registrations determine effective catalogs. The fake deliberately does not invent a sticky provider catalog cache. No adapter/manager method under test is mocked.

| Frozen-base case                                                         | Result                    |
| ------------------------------------------------------------------------ | ------------------------- |
| Adapter F0: child tool immediately after native fork; parent intact      | FAIL, empty child catalog |
| Adapter F1: first prompt own identity; parent/ordinary isolation         | PASS                      |
| Adapter restart/resume, credential rotation, effective deduplication     | PASS                      |
| Registration unavailable, observable warning and recovery                | PASS                      |
| Service F0: actual manager issues scoped auth, child tool at fork return | FAIL, empty child catalog |
| Service F1: first prompt own manager-issued identity                     | PASS                      |
| Service restart, revocation, resume and parent integrity                 | PASS                      |

Executed result: **2 failed, 5 passed; exit 1**. Failures are missing capabilities, rather than setup/decoding/timeouts. Fixture typecheck passed. Exact sanitized test output, fixture contents and hashes are in the evidence JSON. F0 is immediately after successful fork return, before a child turn; F1 is the effective catalog when the fake receives the first prompt. Source inspection additionally found that a provider continuation bypasses `prepareTurn`, but that path replays held events; no new first-prompt failure was executed or inferred from that observation.

This establishes an F0 readiness gap. It does **not** establish the issue's sticky F1 behavior: the tested base registers before a normal child prompt and recovers after restart. Under the reviewed preregistration, substituting an F0-only implementation task would change the benchmark's target after inspecting its oracle. The trial therefore stops before independent coding attempts. This is a reproducibility blocker, not a Codex/Bridge routing or permission failure. It does not prove the upstream issue false; a real provider's independently justified snapshot/inheritance behavior may differ from this fake.
